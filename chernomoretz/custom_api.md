# chernomoretz — публично API за фронтенда

ФК Черноморец 1919 (Бургас) — информационен сайт и магазин за сувенири.

Фронтендът НЯМА собствена база. Всичко минава по HTTP към ядрото (devcore).
Този документ описва какво връща ядрото и как се вика. Поддържа се заедно с
кода — при промяна по endpoint се обновява и тук, в същата стъпка.

Тук са само endpoint-ите на проекта (`fk_*`) и ядрените, които проектът
променя. Останалите ядрени endpoint-и са в `core-v4-front.md` в корена на
това repo.

---

## 1. Свързване

```
База (дев):  https://devcore.myexpozy.com/api/
```

Всяка заявка носи хедър, който казва **кой проект** е:

```
Authentication: Basic <saas_key>
```

`saas_key` е един за проекта. НЕ се хардкодва в клиентски код и НЕ се показва в
HTML — държи се на сървъра на фронтенда и заявките минават през негов прокси
слой. Ключът се взима от собственика на проекта, не стои в това repo.

Кой проект се обслужва се определя от `saas_key`-а, а не от домейна — един и
същ URL на ядрото обслужва всички проекти.

За действия от името на потребител се добавя и:

```
Authorization: Bearer <token>
```

Публичните endpoint-и по-долу минават само със `saas_key`. Където трябва вход,
е отбелязано „изисква вход".

### Формат на отговорите

- Списък → чист масив: `[{...}, {...}]`
- Единичен запис (`?id=5` или `/{id}`) → обект
- Единичен запис по **несъществуващ** id → празен обект с `"id": 0` (не е грешка)
- Празен резултат → `[]` (не е грешка)
- Липсваща/невалидна автентикация → `{"errors": ["Failed authorization 3041"]}`
- Непознат endpoint → `{"errors": ["This method is not supported"]}`

Сортиране: `?order_by=<поле>&order_direction=ASC|DESC`.

Всяко поле от обекта може да се подаде и като филтър: `?status_id=1`,
`?season_id=2` и т.н. Числовите полета се сравняват точно, текстовите — по
частично съвпадение.

Датите са низ `YYYY-MM-DD HH:MM:SS`. `date_updated` е `null`, докато записът
не е редактиран.

### Грешки

| Случай | HTTP | Тяло |
|---|---|---|
| липсва или е невалидно задължително поле | 400 | `{"status": 0, "errors": {"[name=\"email\"]": "Моля, въведете …"}}` |
| нужен е вход, а няма | 403 | `{"status": 0, "errors": "Login first v4!"}` |
| нужна е роля, която потребителят няма | 400 | `{"errors": "Failed level authorization 1"}` |
| нужен е id, а не е подаден | 403 | `{"errors": "Id is not set!"}` |
| чужд билет или карта | 403 | `{"status": 0, "error": "Няма достъп до този билет"}` |
| отказ по бизнес логика | 200 | `{"status": 0, "error": "…"}` или `{"status": 0, "error_fields": {…}}` |

Ключовете в `errors` и `error_fields` са CSS селектори (`[name="email"]`) —
показвай съобщението до полето със същото `name`. Текстовете са на български и
са готови за показване.

### Изображения

Всички полета `logo` и `image`, както и елементите на `images`, са **обект
изображение**:

```json
{
  "id": 12,
  "object_id": 5,
  "filename": "chernomorets.webp",
  "sort_order": 0,
  "date_created": "2026-09-18 10:02:11",
  "url": "https://r2.expozy.com/…/chernomoretz/teams/5/chernomorets.webp",
  "url_10x10": "https://r2.expozy.com/…/chernomoretz/teams/5/10x10/chernomorets.webp"
}
```

| Поле | Значение |
|---|---|
| `url` | самата картинка |
| `url_10x10` | миниатюра 10×10 — за размазан фон, докато се зарежда истинската |

Когато картинка няма, обектът **пак идва** — с `"id": 0` и празни `url` и
`url_10x10`. Никога не е `null`. Показвай заместващо изображение, а не счупена
картинка.

### Езици

Сайтът е само на български. Полетата `title` и `description` идват от
системата за съдържание на ядрото и са редактируеми от админа — не ги
хардкодвай на фронта.

## 2. Откъде идват данните

Класирането и мачовете от **първенството** (Втора лига) се внасят **веднъж
сутрин с крон** от външен източник (goal.bg) и се записват в нашите таблици.
Фронтендът чете само от нашето API и никога не чака външния сайт. Ако
източникът е недостъпен, API-то продължава да връща последните внесени данни.

Практическо следствие: данните се менят най-много веднъж на ден (и веднага след
мач, ако кронът се пусне ръчно). Спокойно кеширай отговорите за час-два.

**Купата на България и контролите** източникът не ги дава — въвежда ги админът
на ръка. Те излизат от същия `GET /fk_matches` заедно с мачовете от
първенството и за фронта няма разлика; различават се само по `competition`
(т. 4). Съперниците в тях също се добавят на ръка, затова някои отбори нямат
`external_id` (т. 3).

## 3. Класиране

```
GET /fk_standings
```

Без параметри връща **цялото класиране на Втора лига за текущия сезон**,
подредено по позиция във възходящ ред. Всеки ред носи и отбора си, заедно с
логото му.

### Параметри

| Параметър | По подразбиране | Действие |
|---|---|---|
| `competition_id` | първенството по подразбиране (Втора лига) | класиране на друг турнир |
| `season_id` | текущият сезон | класиране за конкретен сезон |
| `team_id` | — | само редът на един отбор |
| `id` | — | единичен ред по id на записа |
| `order_by` + `order_direction` | `position` ASC | друга подредба (`points`, `goals_for`…) |

### Отговор

```json
[
  {
    "id": 5,
    "season_id": 1,
    "competition_id": 1,
    "team_id": 5,
    "position": 5,
    "played": 9,
    "won": 4,
    "drawn": 3,
    "lost": 2,
    "goals_for": 12,
    "goals_against": 6,
    "points": 15,
    "date_created": "2026-09-17 14:34:46",
    "date_updated": null,
    "team": {
      "id": 5,
      "title": "Черноморец 1919 (Бургас)",
      "external_id": 10171,
      "external_name": "Черноморец 1919 (Бургас)",
      "city": "",
      "is_own": 1,
      "status_id": 1,
      "date_created": "2026-09-17 14:34:46",
      "date_updated": null,
      "logo": {
        "id": 0,
        "object_id": 0,
        "filename": "",
        "sort_order": 0,
        "date_created": "",
        "url": "",
        "url_10x10": ""
      }
    }
  }
]
```

Обектът `team` е **обект отбор** — същата структура идва навсякъде, където има
отбор (мачове, билети, `GET /fk_teams`).

### Полета

| Поле | Значение |
|---|---|
| `position` | позиция в таблицата |
| `played` | изиграни срещи |
| `won` / `drawn` / `lost` | победи / равенства / загуби |
| `goals_for` / `goals_against` | дадени / получени голове — показват се като „12:6" |
| `points` | точки |
| `team.title` | име за показване; редактируемо от админа |
| `team.external_id` | номерът на отбора в източника. **`0` при отбор, добавен на ръка** (съперник от Купата или контрола) |
| `team.external_name` | суровото име от източника — за вътрешна справка, не го показвай. Празно при отбор, добавен на ръка |
| `team.city` | град; може да е празен |
| `team.is_own` | `1` за Черноморец — по него подчертай реда на нашия отбор |
| `team.status_id` | `1` активен, `0` неактивен |
| `team.logo` | обект изображение (т. 1); **празен**, докато не се качи от админа |

Голова разлика не се връща като отделно поле — сметни я от `goals_for` и
`goals_against`.

### Бележки за фронта

- **Не разчитай на реда в масива по друг начин освен по `position`.** Подредбата
  по подразбиране вече е по позиция, но при подаден `order_by` се сменя.
- Класирането има смисъл само за турнири от тип първенство. За Купата на
  България отговорът ще е празен масив — там се играе на елиминации.

## 4. Мачове — програма и резултати

```
GET /fk_matches
```

**Само мачовете на Черноморец**, не цялата програма на лигата. Програмата и
резултатите са едно и също нещо — разликата е `is_played`. Идват мачовете от
всички турнири: първенство, Купа на България и контроли.

### Параметри

| Параметър | Действие |
|---|---|
| `type=upcoming` | предстоящи (`is_played = 0`), подредени по дата **възходящо** — най-близкият пръв |
| `type=past` | изиграни (`is_played = 1`), подредени по дата **низходящо** — най-новият пръв |
| `competition_id` | само от един турнир |
| `season_id` | по подразбиране текущият сезон |
| `id` | единичен мач |

Без `type` идват всички, хронологично. Няма пагинация — сезонът е около 34 мача
плюс купата и контролите, вземи ги наведнъж и режи колкото ти трябват (например
първите 3 за блок „следващи мачове").

### Отговор

```jsonc
[
  {
    "id": 1,
    "season_id": 1,
    "competition_id": 1,
    "round": 10,
    "date_start": "2026-09-20 20:30:00",
    "has_time": 1,
    "home_team_id": 7,
    "away_team_id": 5,
    "home_goals": 0,
    "away_goals": 0,
    "is_played": 0,
    "date_created": "2026-09-17 14:34:46",
    "date_updated": null,
    "home_team": {
      "id": 7,
      "title": "Етър ВТ (Велико Търново)",
      "external_id": 10165,
      "external_name": "Етър ВТ (Велико Търново)",
      "city": "Велико Търново",
      "is_own": 0,
      "status_id": 1,
      "date_created": "2026-09-17 14:34:46",
      "date_updated": null,
      "logo": { "id": 0, "object_id": 0, "filename": "", "sort_order": 0, "date_created": "", "url": "", "url_10x10": "" }
    },
    "away_team": {
      // обект отбор — същата структура като home_team
    },
    "competition": {
      "id": 1,
      "title": "Втора лига",
      "bfu_slug": "second",
      "goal_group": "2000000/100",
      "type_id": 1,
      "sort": 1,
      "status_id": 1,
      "date_created": "2026-09-17 14:22:44",
      "date_updated": null
    }
  }
]
```

`home_team` и `away_team` са обект отбор (т. 3), `competition` — обект турнир
(т. 11).

### Полета

| Поле | Значение |
|---|---|
| `round` | номер на кръга — източникът го дава с римска цифра, тук е число. **`0` при контроли** |
| `date_start` | дата и час на срещата |
| `has_time` | `0` означава, че **часът още не е обявен** — покажи само датата, не `00:00` |
| `is_played` | `1` = има резултат; `0` = предстоящ |
| `home_goals` / `away_goals` | имат смисъл само при `is_played = 1`; иначе са `0` |
| `competition.title` | името на турнира — „Втора лига", „Купа на България", „Контроли" |
| `competition.type_id` | `1` първенство, `2` купа (елиминации), `3` контрола |

### Бележки за фронта

- **Домакинство или гостуване** се определя от `home_team.is_own`. Ако е `1` —
  играем у дома (бутон „Билети"); иначе гостуваме.
- **Надписът над резултата** се сглобява от `competition.title` и `round`:
  „Втора лига · 10 кръг". При `round = 0` (контроли) кръг не се изписва.
- **Мачът не носи стадион.** Източникът не го дава, а алтернативният е
  недостъпен от сървъра — затова в програмата и резултатите място за стадион не
  се предвижда. Изключение са **билетите**: там админът избира стадион ръчно и
  той идва в `stadium` (виж т. 7), защото купувачът трябва да знае къде да отиде.
- `has_time = 0` се случва редовно за по-далечните кръгове — програмата излиза
  с дати седмици преди часовете. Изобщо не показвай час в този случай.
- Разделянето на „програма" и „резултати" прави API-то, не фронтът — ползвай
  `type`, не сравнявай дати сам.
- Ако страницата има табове по турнир, вземи ги от `GET /fk_competitions` и
  филтрирай с `competition_id`.

## 5. Състав и профил на футболиста

### Съставът (публичен)

```
GET /fk_players
```

Връща активните футболисти, вече подредени **по позиция** (вратари, защитници,
полузащитници, нападатели) и после **по номер на фланелката** — точно реда на
страницата „Отбор". Не пренареждай сам.

| Параметър | Действие |
|---|---|
| `squad_id` | само една формация — първи отбор, дубъл, U19… |
| `id` | единичен играч |

```json
[
  {
    "id": 1,
    "user_id": 34,
    "squad_id": 1,
    "position_id": 4,
    "name": "Живко Петков",
    "email": "",
    "number": 9,
    "is_captain": 1,
    "nationality": "България",
    "date_birth": null,
    "status_id": 1,
    "sort": 0,
    "description": "",
    "date_created": "2026-09-17 15:10:02",
    "date_updated": null,
    "image": { "id": 0, "object_id": 0, "filename": "", "sort_order": 0, "date_created": "", "url": "", "url_10x10": "" },
    "squad": {
      "id": 1, "title": "Първи отбор", "sort": 1, "status_id": 1,
      "date_created": "2026-09-17 15:00:00", "date_updated": null
    },
    "position": {
      "id": 4, "title": "Нападател", "sort": 4, "status_id": 1,
      "date_created": "2026-09-17 15:00:00", "date_updated": null
    }
  }
]
```

| Поле | Значение |
|---|---|
| `name` | име и фамилия |
| `number` | номер на фланелката; `0` значи, че още не е зададен |
| `is_captain` | `1` → показва се етикет „Капитан" |
| `nationality` | **свободен текст**, не код на държава. Попълнено е за всички, включително „България" — ако дизайнът показва националност само за чужденците, фронтът решава кое да скрие |
| `date_birth` | `YYYY-MM-DD`; може да е `null`, докато играчът не си я попълни |
| `description` | кратък текст за играча, пише го самият той |
| `status_id` | `1` активен, `2` напуснал. Списъкът връща само активните, но `?id=` връща и напуснал играч — провери полето |
| `squad` | формацията — `{id, title, sort, status_id, date_created, date_updated}` |
| `position` | позицията — същата структура като `squad` |
| `image` | обект изображение (т. 1); празен, докато няма качена снимка |
| `user_id` | акаунтът на играча; `0`, ако още няма. Служебно |
| `email` | служебно — за акаунта на играча. **Не го показвай на сайта** |
| `sort` | служебно; подредбата вече е приложена |

Групирането по позиция го прави фронтът — вземи `position.title` за заглавие на
групата, а `position.sort` пази реда, ако решиш да групираш сам.

### Профилът (за влезлия футболист)

Футболистите са потребители със своя роля. След вход:

```
GET  /fk_player_profile   (изисква вход)
POST /fk_player_profile   (изисква вход с роля футболист)
```

`GET` връща записа на **логнатия** играч — не приема `id`. Структурата е като
един елемент от `/fk_players`. Ако влезлият не е футболист, идва празен обект
с `"id": 0`.

`POST` приема **само четири неща** и нищо друго:

| Поле | |
|---|---|
| `nationality` | текст |
| `date_birth` | `YYYY-MM-DD`; празно я изчиства |
| `description` | текст |
| `image` | файл, `multipart/form-data` |

Номер, позиция, формация и статус се управляват само от админа. Ако ги
подадеш, сървърът ги пренебрегва — не е грешка във фронта, а нарочно.

Записът се намира по сесията, затова чужд профил не може да се редактира,
каквото и да е подадено в тялото на заявката.

Отговор при успех — обновеният запис:

```jsonc
{ "status": 1, "obj": { /* обект футболист — като в /fk_players */ } }
```

| Случай | Отговор |
|---|---|
| не е влязъл / не е футболист | `400` `{"errors": "Failed level authorization 1"}` |
| влязъл с роля футболист, но без запис в състава | `{"status": 0, "error": "…"}` |

**Не всеки играч има акаунт.** Съставът беше пренесен без имейли, затова има
записи с `user_id = 0` — те се показват в състава като всички останали, но няма
кой да влезе в тях. Акаунтът се създава в мига, в който админът попълни имейл.

**Първи вход:** щом играчът получи имейл, на него тръгва покана с линк за
задаване на парола, валиден 7 дни. Линкът води към ядрената страница
`/bg/forgotten-password?tab=recover&code=…` — същият екран, на който всеки
потребител си задава парола. Не прави втори.

## 6. Ръководство и треньорски щаб

```
GET /fk_staff
```

Всички, които са около отбора, но не са футболисти — президент, спортен
директор, треньори, физиотерапевт, ръководство и треньори на школата. Един
endpoint пълни и двете страници: „Ръководство и щаб" и „Треньори".

| Параметър | Действие |
|---|---|
| `group_id` | само един раздел |
| `id` | единичен запис |

Връща активните, подредени **по група** (в реда на номенклатурата) и после по
`sort` вътре в групата — тоест президентът стои преди спортния директор, а
ръководството преди щаба. Не пренареждай.

```json
[
  {
    "id": 1,
    "group_id": 1,
    "name": "Спасимир Иванов",
    "job_title": "Президент",
    "sort": 1,
    "status_id": 1,
    "description": "",
    "date_created": "2026-09-17 16:00:00",
    "date_updated": null,
    "image": { "id": 0, "object_id": 0, "filename": "", "sort_order": 0, "date_created": "", "url": "", "url_10x10": "" },
    "group": {
      "id": 1, "title": "Ръководство", "sort": 1, "status_id": 1,
      "date_created": "2026-09-17 16:00:00", "date_updated": null
    }
  }
]
```

| Поле | Значение |
|---|---|
| `name` | име и фамилия |
| `job_title` | длъжността, **свободен текст** — не е номенклатура и не разчитай на фиксиран списък |
| `description` | кратък текст; може да е празен |
| `group` | разделът — `{id, title, sort, status_id, date_created, date_updated}`; `group.title` е заглавието на групата на страницата |
| `image` | обект изображение (т. 1); празен, докато няма качена снимка |
| `sort` | редът вътре в групата; вече е приложен |

Групите се теглят отделно, ако ти трябват за навигация или табове:

```
GET /fk_staff_groups
GET /fk_staff_groups?id=1
```

Връща активните, по `sort`, със същата структура като `group` горе —
Ръководство, Треньорски щаб, Ръководство на школата, U19, U17, U15, U13, U11.
Админът може да добави още.

**Тези хора нямат акаунти.** За разлика от футболистите щабът не влиза никъде и
не си редактира профила — всичко се въвежда от админа.

## 7. Билети

### Какво се продава

```
GET /fk_ticket_products
```

Билетите, пуснати в продажба. Връща **само тези, които още се купуват** —
активни, с останала наличност и за мач, който не е започнал. Тоест фронтът не
проверява нищо сам: каквото дойде, се показва.

| Параметър | Действие |
|---|---|
| `match_id` | билетите за конкретен мач |
| `id` | единичен запис — идва дори продажбата да е спряла |

**Абонаментните карти НЕ са тук.** Те са отделен обект със свои endpoint-и —
виж т. 8.

```jsonc
[
  {
    "id": 1,
    "product_id": 42,
    "match_id": 11,
    "stadium_id": 1,
    "is_external": 0,
    "external_url": "",
    "category_id": 7,
    "date_start": "2026-09-27 17:00:00",
    "date_manual": 1,
    "quantity": 500,
    "status_id": 1,
    "date_created": "2026-09-21 12:00:00",
    "date_updated": null,
    "match": {
      // обект мач — пълната структура е в т. 4 (с home_team, away_team, competition)
    },
    "stadium": {
      "id": 1,
      "title": "Стадион „Лазур“",
      "city": "Бургас",
      "address": "",
      "sort": 1,
      "status_id": 1,
      "date_created": "2026-09-21 12:00:00",
      "date_updated": null
    },
    "available": 473,
    "price": 10
  }
]
```

| Поле | Значение |
|---|---|
| `is_external` | **`1` значи, че продажбата е през чужда платформа** — виж долу |
| `external_url` | адресът ѝ; има смисъл само при `is_external = 1` |
| `product_id` | **това слагаш в количката** — билетът е обикновен продукт в магазина |
| `quantity` | колко билета са пуснати общо. При външна продажба не значи нищо |
| `available` | колко остават; когато стигне 0, записът изчезва от отговора. При външна продажба **не значи нищо** |
| `price` | цената на билета в евро — **попълнена е и при външна продажба** |
| `date_start` | началото на мача, което върви върху билета; по него спира продажбата |
| `date_manual` | `1` = часът е зададен ръчно от админа; `0` = следва датата на мача |
| `match` | обект мач (т. 4) |
| `stadium` | къде се играе — изписва се и върху билета |
| `category_id` | служебно — категорията „Билети" в магазина |
| `status_id` | `1` активен; неактивните не идват в списъка |

### Двата случая на бутона „Билети"

В началото клубът продава през **външна система**, затова фронтът трябва да
поддържа и двата пътя. Разликата се вижда от `is_external`:

| `is_external` | Какво прави бутонът |
|---|---|
| `1` | извежда към `external_url` — нов таб, чужд сайт. Нищо не се слага в количката, билет при нас не се издава и в „Моите билети" няма да се появи |
| `0` | добавя `product_id` в количката по обикновения път на магазина |

Ако `is_external = 1`, **не показвай наличност и не се опитвай да купуваш** —
`available` е наше поле и при външна продажба не отразява нищо. Записът и без
това излиза в отговора само докато има валиден линк и мачът не е започнал.

Това се превключва за всеки мач поотделно, тоест може един мач да е навън, а
следващият вече при нас. Не го кеширай като глобална настройка. Същото важи и
за абонаментната карта.

**Цената идва и при външна продажба.** `price` е попълнено независимо от
`is_external` — показвай я до бутона към чуждата платформа, за да не праща
хората да я търсят там.

`product_id` е попълнено винаги, но **при `is_external = 1` не го слагай в
количката** — продуктът съществува само за да носи цената и снимките и е
неактивен в магазина. Решението взимай по `is_external`, не по `product_id`.

### Билетите на купувача

```
GET  /fk_my_tickets     (изисква вход)
GET  /fk_ticket/{id}    (изисква вход)
```

`fk_my_tickets` връща масив от билетите на **влезлия** потребител. Не приема
`user_id` — взима го от сесията, затова чужди билети не могат да се поискат.
Връща **всички** билети, включително анулираните — подай `?status_id=1`, ако
искаш само валидните, или ги покажи с етикет.

`fk_ticket/{id}` връща един билет — за страницата, на която го показваш едър.
Отдава се само на собственика му; чужд билет връща `403`.

**PDF не се генерира.** Сървърът връща данните, а как изглежда билетът е
**твой шаблон**. Записът носи всичко нужно за него:

```jsonc
{
  "id": 1,
  "code": "6956338201595706",
  "ticket_product_id": 3,
  "match_id": 4,
  "order_id": 3,
  "order_item_id": 5,
  "user_id": 12,
  "price": 10,
  "status_id": 1,
  "date_created": "2026-09-23 16:40:12",
  "date_updated": null,
  "match": {
    // обект мач (т. 4) — тук съкратено
    "round": 13,
    "date_start": "2026-10-24 00:00:00",
    "has_time": 0,
    "home_team": { "title": "Черноморец 1919 (Бургас)", "is_own": 1, "logo": { } },
    "away_team": { "title": "Спортист 2009 (Своге)", "is_own": 0, "logo": { } }
  },
  "ticket_product": {
    // обект от /fk_ticket_products — тук съкратено
    "id": 3,
    "date_start": "2026-10-24 17:00:00",
    "stadium": { "id": 1, "title": "Стадион „Лазур“", "city": "Бургас" }
  },
  "code_formatted": "6956 3382 0159 5706",
  "qr": "1"
}
```

| Поле | За какво е |
|---|---|
| `code` | номерът, суров — 16 цифри |
| `code_formatted` | същият, разреден по четири — за показване |
| `qr` | **какво да кодираш в QR кода** — вземай стойността оттук, не я сглобявай сам |
| `price` | платената цена в евро |
| `ticket_product.date_start` | **часът, който върви върху билета** |
| `ticket_product.stadium` | стадионът — мачът не носи стадион, билетът да |
| `match.home_team` / `away_team` | имената и емблемите |
| `status_id` | `1` валиден, `2` използван, `3` анулиран |
| `order_id` | поръчката, с която е купен — за връзка към „Моите поръчки" |
| `order_item_id`, `ticket_product_id`, `user_id` | служебни |

**Кой час да показваш:** `ticket_product.date_start`, не `match.date_start`.
Мачът често няма обявен час (`has_time: 0` и време `00:00`), а админът задава
часа на билета ръчно.

**QR кодът** се рисува на фронта — сървърът не връща изображение. Кодирай
**точно стойността на `qr`**, без да я променяш.

Засега `qr` е равно на id-то на билета (`"1"`), но това **ще се смени** —
форматът още не е уточнен с клиента и може да стане подписан низ или URL за
проверка. Затова не строй QR-а от `id` или `code` на фронта: вземаш `qr` както
е и го подаваш на библиотеката. Така смяната няма да изисква работа по фронта.

Ако се окаже по-удобно сървърът да връща готово изображение (base64), казваш и
се добавя като отделно поле — `qr` ще си остане.

| Случай | Отговор |
|---|---|
| не е влязъл | `403` `{"status": 0, "errors": "Login first v4!"}` |
| чужд билет | `403` `{"status": 0, "error": "Няма достъп до този билет"}` |
| без id | `403` `{"errors": "Id is not set!"}` |

### Бележки за фронта

- **Един билет = един запис.** Купувач с три броя получава три реда с три
  номера. Не ги групирай — на входа тримата влизат поотделно.
- **Билетът не е файл** и не се пази като такъв. Отваря се всеки път наново от
  данните, затова преместен мач сам излиза с верния час.
- **Билетите излизат в момента, в който поръчката стане платена.** Няма
  закъснение — щом плащането се отбележи (от админа или от платежния
  доставчик), билетите вече са в `/fk_my_tickets`. Докато поръчката не е
  платена, списъкът е празен: покажи, че поръчката се обработва.

### Стадиони

```
GET /fk_stadiums
GET /fk_stadiums?id=1
```

Активните, по `sort`. Структурата е същата като `stadium` в билета:
`{id, title, city, address, sort, status_id, date_created, date_updated}`.
Обикновено не ти трябва отделно: билетът вече носи своя стадион.

## 8. Абонаментни карти

Картите са **отделни от билетите** — своя структура, свои endpoint-и, свой
раздел на сайта. Не ги смесвай с билетите и не ги показвай в „Моите билети".

### Какво се продава

```
GET /fk_season_passes
GET /fk_season_passes?id=1
```

Връща само това, което още се купува. **Един сезон има няколко вида карти** —
по сектори — подредени по `sort`. Единичният запис по `id` идва дори продажбата
да е спряла.

```json
[
  {
    "id": 1,
    "product_id": 43,
    "season_id": 1,
    "title": "Синя · Сектор В",
    "is_external": 0,
    "external_url": "",

    "season": {
      "id": 1, "title": "2026/2027", "bfu_name": "2026-2027", "is_current": 1,
      "status_id": 1, "date_created": "2026-09-17 14:22:44", "date_updated": null
    },
    "images": [
      {
        "id": 4,
        "object_id": 43,
        "filename": "karta-sinya.webp",
        "sort_order": 0,
        "date_created": "2026-09-23 11:00:00",

        "url_10x10": "https://r2.expozy.com/…/10x10/karta-sinya.webp",

        "data_id": 0,
        "external_id": "",
        "color_id": 0
      }
```

| Поле | Значение |
|---|---|
| `title` | името на картата — „Синя · Сектор В". Идва от продукта в магазина |
| `images` | снимките на продукта; вземай първата. Празен масив, докато няма качена. Освен полетата на обекта изображение (т. 1) носят и служебни `alt`, `data_id`, `external_id`, `color_id` |
| `price` | цената в евро — **връща се и при външна продажба** |
| `product_id` | това слагаш в количката — **но само когато `is_external` е `0`** |
| `quantity` | колко карти са пуснати общо |
| `available` | колко остават; при външна продажба не значи нищо |
| `sort` | реда на показване; спазвай го |
| `season` | сезонът, за който важи картата — обект сезон (т. 11) |
| `is_external` / `external_url` | същото както при билетите — бутонът води навън |
| `category_id` | служебно — категорията „Абонаменти" в магазина |

Картата **няма стадион, дата и час**: важи за всички домакински мачове от
първенството, а те са на различни стадиони. Спира да се продава, когато сезонът
ѝ престане да е текущият — не в началото на някакъв мач.

### Картите на купувача

```
GET  /fk_my_cards     (изисква вход)
GET  /fk_card/{id}    (изисква вход)
```

Работят точно като `fk_my_tickets` и `fk_ticket`, но за карти: записът се
намира по сесията и се отдава само на собственика. `fk_my_cards` връща и
анулираните — филтрирай с `?status_id=1`. PDF не се генерира и тук — шаблонът
на картата е на фронта.

```json
{
  "id": 1,
  "code": "4417902263318850",
  "season_pass_id": 1,
  "season_id": 1,
  "order_id": 7,
  "order_item_id": 11,
  "user_id": 12,
  "price": 55,
  "status_id": 1,
  "date_created": "2026-09-24 10:15:00",
  "date_updated": null,
  "season": {
    "id": 1, "title": "2026/2027", "bfu_name": "2026-2027", "is_current": 1,
    "status_id": 1, "date_created": "2026-09-17 14:22:44", "date_updated": null
  },
  "code_formatted": "4417 9022 6331 8850",
  "qr": "1"
}
```

| Поле | Значение |
|---|---|
| `code` / `code_formatted` | номерът на картата — суров и разреден по четири |
| `qr` | какво да кодираш в QR кода — правилата са същите като при билета |
| `season.title` | сезонът, който се изписва върху картата |
| `price` | платената цена в евро |
| `status_id` | `1` валидна, `2` използвана, `3` анулирана |
| `season_pass_id` | видът карта, от който е купена — от него идват името и снимката |
| `order_id`, `order_item_id`, `user_id` | служебни |

**Картата не носи собствено име и снимка** — те са на вида карта. Ако шаблонът
ги показва, вземи ги с `GET /fk_season_passes?id={season_pass_id}`.

Няма отбори, дата и стадион — картата важи за всички домакински мачове от
първенството през сезона, не за конкретна среща.

Грешките са същите като при билетите (`403` за чужда карта, с текст „Няма
достъп до тази карта").

### Какво още не дава

Страницата на сайта обещава и **отстъпка в магазина**, преференциално купуване
на билети за купата и специални събития. Те **не са реализирани** — картата
засега дава само достъп до домакинските мачове. Не строй интерфейс около
привилегии, които сървърът не знае.

## 9. Поръчка

`POST /orders` е ядреният endpoint, но в този проект се държи различно в
няколко неща — описани са тук. Всичко останало е както в `core-v4-front.md`.

### Задължителни полета

`first_name`, `last_name`, `email`, `phone`, `terms`, `payment_method` — винаги.
`address` — само ако в количката има физически продукт (виж долу).

При липсващо поле поръчката не се записва и идва:

```json
{ "status": 0, "error_fields": { "[name=\"phone\"]": "Моля, въведете телефон." } }
```

### Поръчка с регистрация

Поръчка може да се направи и без профил. Но при поръчка с **билет** профил е
задължителен: билетът се отдава само на влязъл купувач и гост няма как да си го
вземе.

За да не се налага човек да минава през отделна регистрация и после наново през
количката, поръчката приема парола:

```
POST /orders
{ …обичайните полета…, "password": "…" }
```

Подадена парола означава „искам и профил". Сървърът създава акаунта, **логва
потребителя** и записва поръчката вече на негово име. Без парола поръчката
минава като гостова, както досега.

### Гост с вече съществуващ профил

Ако поръчва **гост**, а въведеният имейл вече има профил, поръчката се отказва:

```json
{
  "status": 0,
  "error_fields": {
    "[name=\"email\"]": "Вече има профил с този имейл. Моля, влезте в профила си, за да продължите."
  }
}
```

Това важи **независимо дали е подадена парола**. Покажи съобщението и изведи
човека към входа — най-добре с полето за имейл вече попълнено и с връщане към
количката след успешен вход, за да не започва отначало.

### Проверка още при попълването

За да не разбира човекът чак след „Поръчай", същата проверка стои и отделно:

```
POST /fk_email_exists
{ "email": "…" }
```

| Случай | Отговор |
|---|---|
| има профил | `{ "status": 1, "exists": true }` |
| няма профил | `{ "status": 1, "exists": false }` |
| празен или невалиден имейл | `400` `{"status": 0, "errors": {"[name=\"email\"]": "…"}}` |

POST е, а не GET, за да не влиза имейлът в адреса и оттам в логовете.

Извикай я при излизане от полето за имейл. Ако върне `exists: true` и човекът
не е влязъл, покажи поканата за вход веднага, вместо да го оставиш да попълни
цялата форма напразно.

Това е **удобство, не защита** — поръчката прави същата проверка сама и ще
откаже, дори фронтът да я пропусне.

Причината не е формална: ако човек с профил поръча като гост, поръчката няма да
се закачи за акаунта му и купеният билет **няма да се появи** в „Моите билети",
защото се отдава само на влезлия си собственик.

### Какво да очакваш

| Случай | Отговор |
|---|---|
| успех | обичайният отговор на поръчката |
| гост, чийто имейл има профил | `error_fields` по `email` със съобщението горе; **поръчката НЕ е записана** |
| подадена парола, къса под 6 знака | `error_fields` по `password`; **поръчката НЕ е записана** |

При всяка от тези поръчката се отменя цялата. Иначе човек щеше да плати и да
остане без профил, тоест и без билет.

### Бележки

- Паролата е **поне 6 знака** — валидира се на сървъра, но провери и на фронта,
  за да не се губи цяла поръчка заради това.
- Ако имейлът вече има профил, регистрация не става. Тогава или предложи вход,
  или остави човека да поръча като гост — но **не и ако в количката има билет**.
- Потребителят излиза от заявката вече влязъл, с токен. Не го карай да се логва
  наново.

### Поръчка само с дигитални продукти — без адрес и без доставка

Билетите и абонаментните карти са дигитални: стигат до купувача в „Моите
билети", не по куриер. Когато в количката **няма нито един физически
продукт**, `POST /orders` минава без адрес:

```
POST /orders
{ "first_name", "last_name", "email", "phone", "terms", "payment_method", "password"? }
```

`address`, `city`, `post_code`, `country`, офисите на Speedy/Econt/Sameday — **не
се пращат**. Скрий целия блок за доставка на checkout-а, когато количката е само
с билети и карти.

`shipping_price` в отговора е `0`, а `total` е равен на сбора на продуктите.

**Стига един физически продукт** (шал от магазина заедно с билет) и адресът пак
става задължителен — тогава показваш блока за доставка както обикновено и при
липсващ адрес получаваш:

```json
{ "status": 0, "error_fields": { "[name=\"address\"]": "Моля, въведете адрес" } }
```

Как да познаеш дали количката е само дигитална: всеки ред в `GET /cart` носи
`type`; дигиталните са `type: 3`.

### Плащане с карта (Stripe)

При `payment_method` за Stripe поръчката се записва и отговорът носи адреса на
платежната страница:

```jsonc
{
  "status": 1,
  "order_id": 15,
  "redirect": "https://checkout.stripe.com/c/pay/…",
  "url": "https://checkout.stripe.com/c/pay/…",
  "obj": { /* поръчката */ }
}
```

Пренасочи браузъра към `redirect`. След успешно плащане Stripe отбелязва
поръчката като платена и **билетите и картите се издават в същия момент**.

Ако платежната страница не може да се отвори, отговорът е различен от ядрото —
поръчката **вече е записана** и номерът ѝ се връща, за да има какво да каже
клиентът, ако се обади:

```json
{
  "status": 0,
  "order_id": 15,
  "error": "Плащането с карта не можа да започне. Поръчка № 1015 е приета — свържете се с нас, за да я довършим."
}
```

Покажи `error` както е. **Не пускай поръчката наново** — ще се запише втора.

## 10. Школа

Три неща за детско-юношеската школа: възрастовите групи, турнирите и формата
за записване.

### Възрастови групи

```
GET /fk_age_groups
GET /fk_age_groups?id=3
```

Номенклатура — **спри да ги изписваш на ръка във фронта.** Едни и същи групи
се ползват на страницата на школата, при турнирите и в селекта на формата за
записване.

```json
[
  {
    "id": 1,
    "title": "U19",
    "description": "Юноши старша възраст",
    "sort": 1,
    "status_id": 1,
    "date_created": "2026-09-21 10:00:00",
    "date_updated": null
  }
]
```

| Поле | Значение |
|---|---|
| `title` | кодът — „U19", „U8 – U9" |
| `description` | как се нарича групата — „Юноши старша възраст" |
| `sort` | реда; вече е приложен |

Връща само активните, подредени от най-голямата надолу. Админът може да добави
или махне група — не разчитай на фиксиран брой.

### Турнири

```
GET /fk_tournaments?type=upcoming
GET /fk_tournaments?type=past
```

| Параметър | Действие |
|---|---|
| `type=upcoming` | предстоящите — най-близкият най-отгоре |
| `type=past` | приключилите — най-скорошният най-отгоре |
| `age_group_id` | само за една възрастова група |
| `id` | единичен турнир |

Без `type` излизат всички, подредени по начална дата.

```json
[
  {
    "id": 1,
    "age_group_id": 3,
    "title": "International Black Sea Cup",
    "description": "",
    "date_from": "2026-06-01",
    "date_to": "2026-06-05",
    "location": "Бургас, България",
    "sort": 0,
    "status_id": 1,
    "date_created": "2026-09-21 10:00:00",
    "date_updated": null,
    "age_group": {
      "id": 3, "title": "U15", "description": "Момчета", "sort": 3, "status_id": 1,
      "date_created": "2026-09-21 10:00:00", "date_updated": null
    }
  }
]
```

| Поле | Значение |
|---|---|
| `title` / `description` | името и текстът на турнира; описанието може да е празно |
| `date_from` / `date_to` | начало и край, `YYYY-MM-DD` |
| `location` | свободен текст — град, държава |
| `age_group` | възрастовата група — обект като в `/fk_age_groups`. При `age_group_id = 0` идва празен обект с `id: 0` |

Разделянето на предстоящи и минали върви по **крайната** дата, не по началната
— турнир, който тече в момента, остава в „Предстоящи" до последния си ден.

Еднодневните турнири имат `date_to` равно на `date_from`. Когато двете дати
съвпадат, показвай само едната.

`age_group_id = 0` значи, че турнирът не е вързан за група.

### Заявка за записване

```
POST /fk_academy_request
```

Формата „Запиши дете". **Смени я от `post.contacts` на този endpoint** —
ядреният `contacts` пази само `subject` и `message`, тоест името на детето,
годината, групата и телефонът се губеха по пътя.

| Поле | Задължително | Бележка |
|---|---|---|
| `child_name` | да | име на детето |
| `birth_year` | да | година на раждане, число |
| `parent_name` | да | име на родителя — сега полето на фронта се казва `name` |
| `phone` | да | |
| `email` | да | имейл на родителя |
| `age_group_id` | не | id от `/fk_age_groups`; празно = „Не съм сигурен" |
| `message` | не | бележка |

Селектът за възрастова група вече не е с текстови стойности (`U15`) — праща
`id` от `/fk_age_groups`, а опцията „Не съм сигурен" праща празно.

| Случай | Отговор |
|---|---|
| успех | `{ "status": 1, "msg": "…" }` |
| липсващо или невалидно поле | `400` `{"status": 0, "errors": {"[name=\"child_name\"]": "…"}}` |
| писмото не можа да тръгне | `{ "status": 0, "error": "…" }` |

Заявката **не се записва никъде** — препраща се по пощата на клуба, който
после звъни на родителя. Затова няма endpoint за четене на заявки и няма
списък в админа.

## 11. Справочници

Сменят се рядко — кеширай ги. Всички връщат само активните.

### Турнири

```
GET /fk_competitions
GET /fk_competitions?id=1
```

Подредени по `sort`.

```json
[
  { "id": 1, "title": "Втора лига", "bfu_slug": "second", "goal_group": "2000000/100",
    "type_id": 1, "sort": 1, "status_id": 1,
    "date_created": "2026-09-17 14:22:44", "date_updated": null }
]
```

`type_id`: `1` = първенство с класиране, `2` = турнир на елиминации (Купа на
България), `3` = контроли и приятелски мачове.

`bfu_slug` и `goal_group` са вътрешни — идентифицират турнира при външните
източници. Празни са при турнирите, които се въвеждат на ръка. Фронтендът няма
работа с тях.

### Сезони

```
GET /fk_seasons
GET /fk_seasons?id=1
```

Най-новият сезон пръв.

```json
[
  { "id": 1, "title": "2026/2027", "bfu_name": "2026-2027", "is_current": 1,
    "status_id": 1, "date_created": "2026-09-17 14:22:44", "date_updated": null }
]
```

`is_current = 1` е сезонът, който endpoint-ите ползват по подразбиране.
`bfu_name` е вътрешно.

### Формации и позиции

```
GET /fk_squads       → Първи отбор, Дубъл, U19 … U8
GET /fk_positions    → Вратар, Защитник, Полузащитник, Нападател
```

И двете приемат `?id=`, подредени са по `sort` и връщат:

```json
[
  { "id": 1, "title": "Първи отбор", "sort": 1, "status_id": 1,
    "date_created": "2026-09-17 15:00:00", "date_updated": null }
]
```

Съставът вече носи своите `squad` и `position`, така че тези endpoint-и ти
трябват само за филтър или навигация по формации.

### Отбори

```
GET /fk_teams
GET /fk_teams?id=5
```

Нашият отбор и всички съперници, подредени по име. Всеки елемент е обект отбор
— пълната структура е в т. 3. Обикновено не ти трябва отделно — класирането и
мачовете вече носят отборите си.

Съперниците от Купата и контролите се добавят на ръка от админа и при тях
`external_id` е `0`, а `external_name` е празно.

## 12. Ядрени endpoint-и с добавки за проекта

Тези идват от ядрото, но в този проект връщат и едно поле повече.

### Продукти — външен линк за пазаруване

```
GET /products
GET /product?id=5
```

Всичко е като в ядрото (`core-v4-front.md`) — пагинация, филтри, структура на
продукта. Добавено е само:

| Поле | Значение |
|---|---|
| `external_url` | външен линк за пазаруване на продукта; **празен низ**, когато няма |

В `/products` полето е на всеки елемент от `result`, в `/product` — на самия
обект.

Ядрото не прави нищо с линка и не ограничава продукта заради него: продуктът
си остава в количката, в цената и в наличностите както всеки друг. **Какво да
се покаже при попълнен линк решава фронтът** — например бутон „Купи от …" до
или вместо „Добави в количката".

### Спонсори

```
GET /partners
GET /partners?id=1
```

Ядреният endpoint, но тук спонсорът има и **описание**.

```json
[
  {
    "id": 1,
    "title": "Спонсор ООД",
    "description": "Генерален спонсор на клуба от 2024 г.",
    "link": "https://…",
    "status_id": 1,
    "discount": 0,
    "image": {
      "id": 3,
      "object_id": 1,
      "filename": "logo.webp",
      "sort_order": 0,
      "date_created": "2026-09-30 12:00:00",
      "url": "https://r2.expozy.com/…/logo.webp",
      "url_10x10": "https://r2.expozy.com/…/10x10/logo.webp"
    },
    "date_created": "2026-09-30 12:00:00"
  }
]
```

| Поле | Значение |
|---|---|
| `title` | името на спонсора |
| `description` | текст за спонсора; може да е празен |
| `link` | сайтът му — отваряй в нов таб; може да е празен |
| `image` | логото — обект изображение (т. 1) |
| `status_id` | винаги `1` — свалянето от сайта става с триене |
| `discount` | служебно, не се ползва в този проект |

Няма пагинация — връщат се всички наведнъж.

## 13. Какво идва от ядрото

Тези страници НЕ се нуждаят от `fk_` endpoint — ядрото вече ги покрива и
проектът не ги променя:

| Страница | Endpoint |
|---|---|
| Новини, Интервюта | `GET /blogPosts`, `GET /blogCategories`, `GET /blog_comments`, `POST /blog_comments` |
| История, Стадион, Клуб, За школата, Общи условия, Поверителност, Бисквитки | `GET /pages` |
| Галерия | `GET /gallery`, `GET /gallery_categories` |
| Контакти | `GET /contacts`, `POST /contacts` |
| Бюлетин („Абонирай се") | `POST /subscribe` с `email` |
| Магазин | ядрения `shop` — `products` (виж т. 12), `cart`, `orders` (виж т. 9) |
| Спонсори | `GET /partners` — виж т. 12 |

**Новините** са в категория „Новини" (`id = 1`). Админът ги пуска и през
„Бърза новина" — тя записва обикновена публикация в блога, текстът е в
`description` във формата на ContentBuilder. За фронта няма разлика от
останалите публикации.

Билетите и абонаментните карти **също излизат от `GET /products`**, защото са
продукти в магазина (категории „Билети" и „Абонаменти", `type: 3`). За
собствените им страници обаче ползвай `fk_ticket_products` и `fk_season_passes`
— те носят мача, стадиона, часа и оставащата наличност, каквито продуктовата
карта няма.

Страницата „Фенове" е само хъб с връзки — няма свои данни.

„Треньори" на школата също излизат от `GET /fk_staff` — филтрират се по
`group_id`.

## 14. Какво още няма

Тези данни са договорени, но още не са реализирани. Не ги чакай от API-то:

- голмайстори и статистика на играчите
- сектори на стадиона и места по билетите
- привилегиите на абонаментната карта (т. 8)

Плащането с карта (Stripe) е вързано (т. 9), но целият път с тестова карта —
поръчка, плащане, издаден билет — още не е минат. Докато не бъде, тествай
checkout-а и с наложен платеж.
